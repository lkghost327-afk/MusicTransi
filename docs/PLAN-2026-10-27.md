## 1. Outcome and priorities

Make Android Auto dependable, provide searchable song choices on supported car
screens, improve recommendation relevance, make Activity useful and visually
appealing, and make the whole Android interface fit and move consistently.

| Priority | Deliverable | Completion evidence |
|---|---|---|
| P0 | Reliable car playback and a search-capable media contract | Cold-start, search, control and reconnect tests; actual head-unit check |
| P0 | Trustworthy listening data shared by Activity and recommendations | Deterministic clock, attribution, persistence and migration tests |
| P1 | Better candidate supply, recording identity and personalised ranking | Before/after fixtures, complete mixes with ≥10 eligible unique recordings |
| P1 | Responsive phone/tablet layouts and richer Activity | Screenshot/layout matrix, accessibility checks and user feedback |
| P1 | Consistent motion with less jitter | Repeatable device traces and before/after frame measurements |
| Conditional | Explicit custom car Search button and parked keyboard | Host support, distribution eligibility and parked/moving tests |

Android is the implementation target for this cycle. Design tokens and data
definitions should be reusable, but SwiftUI changes, Apple CarPlay and iPhone
feature parity require a separate implementation/test pass. No iOS work should
be reported as complete because Android screens have changed.

Policy record: planning=deep; context_depth=dependency; verification_depth=impact;
delegation=read-only investigators for car integration and recommendation research.
Today's write scope is this plan only. Existing v0.13 source changes remain intact.
The user explicitly requested saving the plan; no app edits, builds, releases,

## 2. Baseline we will preserve

The local v0.13 Android preview is the starting point, not a clean Git checkout.
It contains the exported car browser, voice play-from-search, frosted surfaces,
word-follow lyrics and a first monthly Activity implementation. Its recorded
verification is 36 passing local tests, four skipped network tests and lint with
zero errors/22 warnings. The car-browser instrumentation test compiled but did
not run on a connected phone or car. This is not evidence of real-car readiness.

Keep its APK, source archive, hash and signing identity. Do not uninstall the
user's app, discard the current working changes, reset the library, or delete
previously collected Activity data. Create the next development checkpoint only
after inspecting the existing changes; use a `codex/` branch when branching.

### Observed weaknesses in the current source

| Area | Evidence | Planned consequence |
|---|---|---|
| Home suggestions | `HomeSuggestions` takes up to eight, but its default loader requests only three | Separate shelf requests from the three-song autoplay buffer |
| Sparse suggestions | `recommendationBatch` can accept one candidate and stop early | Continue bounded retrieval until the requested eligible count or a real limit |
| Taste profile | History retains 80 distinct recordings; replays only reorder them | Add qualified plays, heard time and explicit feedback |
| Request scheduling | `YouTubeSource` holds one mutex across network work and resolution | Protect playback from background discovery delays |
| Car search | Native `MediaBrowserService`, root extras null, voice-only `onPlayFromSearch` | Add a real browsable search contract through a compatible service adapter |
| Car recovery | Item selection depends on in-memory maps; lists stop at 100 | Persistent IDs, visible errors and host-aware paging |
| Activity data | Month/song totals in SharedPreferences JSON, no day or play counts | Transactional aggregates and a carefully migrated event foundation |
| Activity timing | `AudibleClock` clamps gaps to 1 second | Revisit valid long intervals, stalls, track changes and pause boundaries |
| Activity cost | Month lookup happens in the 40 ms player loop; JSON encoding occurs in `flush()` | Move storage/aggregation out of the playback/UI hot path |
| Layout | Fixed 268×310 cards, 156 dp covers, five bottom tabs, fixed paddings | Window-aware composition and a short-screen layout |
| Motion | Nested cover crossfades, separate duration choices, whole playback state passed to `MusicScreen` | Profile first; isolate rapidly changing state and coordinate motion |

These are code observations and risks, not measured claims that every one causes
a visible failure. Collect reproduction steps and traces before attributing jank.

## 3. What we learned from the Spotify APK

The supplied APK was inspected statically without running it or accessing an
account. The ZIP contains 4,834 entries and 17 DEX files (153,798,178 bytes).
Observed resources include:

- `res/layout/recommendations_page.xml` and its header.
- `res/layout/search_recommendation_card.xml`.
- `res/layout/smartshuffle_recommendations_card.xml`.
- Recommendation-disable bottom-sheet layouts.

Observed DEX reference names include `CurationRecommendationsRequest`,
`ItemSpecificRecommendationsRequest`, `SuggestedTracks`, `SuggestedByGenre`,
`RecommendationUrisResponse`, `RecommendedSearchesResult`, `TasteProfilePage`
and `CollectionItemdata$BanItemData`. These are client-interface clues, not proof
that each feature is active or a recovered ranking algorithm.

**Useful design lesson:** different listening contexts need different candidate
sources/ranking, persistent preferences, and controls for unwanted suggestions.
The APK does not reveal Spotify's server training data, model weights or complete
ranking formula. We will implement our own small, explainable recommender rather
than promise to transplant Spotify's algorithm.

Spotify's public engineering account describes candidate generation followed by
ranking for Home. That supports the architectural separation below; it does not
describe the exact current APK's backend. [Spotify Engineering](https://engineering.atspotify.com/2021/11/the-rise-and-lessons-learned-of-ml-models-to-personalize-content-on-home-part-i)

Spotify also publicly lists listening and interaction signals and preference
controls. We will use local playback/feedback signals without importing unrelated
personal information. [Understanding recommendations](https://www.spotify.com/uk/safetyandprivacy/understanding-recommendations)

Before further APK work, write a small evidence note with the APK hash and exact
entry/type names. Only pursue an additional static inspection when it answers a
specific implementation question. No proprietary code/assets, private API calls,
account tokens or claims of recovered server models are needed.

## 5. Phase B — Android Auto reliability and search

### B1. Fix the shared catalogue contract

Introduce a car-facing catalogue repository backed by the same library, search
and recording identities as the phone. It supplies stable media IDs, metadata,
artwork and ordered collections; it does not own another audio player.

- Resolve a selected ID after service recreation without first rebuilding an
  in-memory browse map. Unknown, removed or expired IDs produce a visible error.
- Keep bounded caches and request lifetimes. Cancel stale requests and discard
  out-of-order results when the query or browser subscription changes.
- Support loading, empty, offline, partial and retry states. Offer saved/offline
  items when a provider search cannot run.
- Apply host item limits and paging instead of silently truncating every list at
  100. Keep current item, queue, liked state and artwork updates consistent.
- Test audio focus, foreground service lifetime, lockscreens and notification
  commands. Retain the notification-command token protection and caller checks.

### B2. Add search-and-select separately from voice play

Typing a search must not pause the current song or replace its queue. Show results
first; play only after selection. Voice commands that explicitly request playback
continue through a separate play-from-search path.

Use the standard search-support declaration and browser/library search callbacks
so supporting hosts can display queries and selectable results. The documented
legacy key is `MediaConstants.BROWSER_SERVICE_EXTRAS_KEY_SEARCH_SUPPORTED`.
Advertising the key alone is insufficient: the corresponding search callbacks
must work. [Browsable search](https://developer.android.com/training/cars/media/create-media-browser/browsable-search)

Our native framework service cannot gain the compat `onSearch` method by adding
an override. First perform a small adapter prototype:

1. Prefer Media3 `MediaLibraryService`/`MediaLibrarySession` search support with
   a logical `Player` facade over the existing two-deck engine.
2. The facade must report one coherent current item, timeline, transport state,
   position and queue while deck ownership changes internally. Avoid two active
   public media sessions or duplicate notifications.
3. Gate adoption on pause/seek/skip, blend handoff, focus, notification and resume
   regression tests. Do not replace the engine with one ExoPlayer for convenience.
4. Evaluate a minimal Compat bridge only as a documented temporary alternative
   if the facade exposes unacceptable regression risk. Current AndroidX marks
   MediaBrowserServiceCompat deprecated; verify the chosen dependency versions
   and migration route before committing to it. [Compat API](https://developer.android.com/reference/androidx/media/MediaBrowserServiceCompat)

The standard host owns the screen and input affordances. A working browser search
contract does not guarantee a particular Search button or keyboard on every car.

### B3. Decision gate for the requested explicit Search button

Test standard search on the actual host first. If it cannot provide the requested
parked typing experience, investigate a separate Car App Library (CAL) prototype:

- Search action → SearchTemplate → selectable song/album results → Now Playing.
- Debounce text changes (initial design target: 300 ms), cancel earlier queries,
  preserve existing playback, and provide recent selections when the field is empty.
- Let the host determine keyboard availability. Google's SearchTemplate allows
  its keyboard while parked; moving-state access uses voice and previous results.
  [SearchTemplate rules](https://developers.google.com/cars/design/create-apps/apps-for-drivers/templates/search-template)
- Check CAL API 8+ support for MediaPlaybackTemplate, the MEDIA category,
  MEDIA_TEMPLATES permission, attribution icon and session registration.
  [Templated media implementation](https://developer.android.com/training/cars/apps/media)
- Recheck distribution before promising a downloadable custom-template build.
  Google's current design page labels templated media beta/internal-and-closed
  Play testing; its Unknown sources testing exception excludes CAL apps.
  Existing GitHub sideload instructions therefore cannot be assumed sufficient.
  [Media options](https://developers.google.com/cars/design/create-apps/app-types/media),
  [Car testing and distribution](https://developer.android.com/training/cars/testing)

Keep the standard browser build available until these gates are satisfied. Do
not implement a fake Search folder that cannot open input, or claim an arbitrary
Compose keyboard can be placed inside Android Auto's standard media screen.

### B4. Car acceptance matrix

Test cold start without opening the Activity, phone locked/backgrounded, process
recreation, disconnect/reconnect, cached/offline content, large playlists,
expired artwork, source failure, audio-focus interruptions and repeated commands.
Check play/pause, previous/next, seek, like, queue order and steering-wheel controls.
Search cases: blank, Unicode, long query, no results, timeout, cancellation and an
older response arriving last. Searching must leave playback unchanged until selection.
Security cases: unknown caller, invalid ID and unauthorised raw notification intent.

Use the Desktop Head Unit for available short/tall/wide and touch/rotary scenarios,
then verify while parked on the actual car, including supported parked typing
and moving-state restrictions. A compiled test or phone screenshot is not a car
compatibility pass. Prefer DHU/connected devices over reinstalling a large emulator.

## 6. Phase C — accurate, durable listening data

Use one listening recorder for Activity and recommendations. Separate duration
accounting, qualification rules, storage and presentation so future user feedback
does not require another database rewrite.

1. Give each play instance an ID. Record track/recording identity, playback origin
   (manual, queue, autoplay), monotonic elapsed time, wall timestamp and timezone.
2. Account for audible intervals at pause, buffering, seek, track switch, stop and
   focus loss. Investigate the one-second clamp rather than silently counting or
   discarding all long gaps. Use playback evidence to distinguish a blocked UI
   thread from stopped audio. Scrubbing never adds listening minutes.
3. Define qualified play, completion, intentional replay and early manual skip
   before weighting recommendations. Initial qualified-play rule: 30 seconds,
   or half the duration for a shorter track. Unknown durations use 30 seconds.
   Completion must not be inferred simply from seeking to the end. Treat calls,
   buffering/errors and external interruptions separately from dislikes.
4. Count overlap once. Retain v0.13's outgoing-track attribution until the logical
   handoff for now; document it and test it. If we later choose volume-weighted
   allocation, the total elapsed time must remain conserved.
5. Split intervals at calendar boundaries using an explicit timezone policy.
   Use monotonic time for duration; record timezone changes as new segments rather
   than silently rebucketing history. Test midnight, month/year rollover, DST and
   manual wall-clock changes with injected clocks.
6. Store aggregates in SQLite through an IO repository, following the existing
   LibraryStore approach. Keep current-session checkpoints idempotent and update
   aggregates transactionally, not by rewriting every historical row on each tick.
7. Proposed retention: monthly/daily aggregates up to 24 months, a bounded recent
   session journal (30 days/5,000 sessions), and a small derived taste snapshot.
   Finalise limits after measuring size; journal expiry must not delete totals.
8. Migrate v0.13 monthly totals exactly once with a schema/migration marker and
   transaction. Preserve them as legacy monthly totals. Do not invent historical
   daily bins, completions or play counts that were never recorded.
9. Keep the old data until migration read-back succeeds; test interruption/retry,
   database reopen, corrupt rows and duplicate migration. Test update installation
   separately; APK downgrades alone are not a database rollback strategy.
10. Provide reset/clear controls with defined scope. Clearing Activity must not
    delete playlists; deleted events must not repopulate totals or keep influencing
    a derived profile unexpectedly. Keep processing local.

Exit: scripted playback sessions produce the expected totals without duplicate
credit; migration preserves existing minutes; storage work does not run at 25 Hz.

## 7. Phase D — recommendations that follow listening intent

Pipeline: listening signals → local taste snapshot → candidate retrieval → identity
and eligibility → context-specific ranking → diversity/repetition checks → display/queue.

### D1. Fix candidate supply and scheduling

- Give autoplay buffering, Home shelves and mixes distinct requested counts. Fix
  the three-versus-eight Home mismatch first, with a regression fixture.
- Gather candidates from current-song radio, recent qualifying artists, liked
  artists and a bounded related-artist expansion. Do not label inferred artists
  or release dates as known facts.
- Start with a metadata candidate budget around 150 and a capped request budget;
  tune using latency/coverage measurements. Fetch only enough to satisfy the
  eligible result target, with caching, request coalescing and backoff.
- Audit extractor global state before changing the mutex. Preserve necessary
  serialization, separate safe independent radio HTTP work, and prioritise
  selected-track resolution/preloading over background discovery. Do not simply
  delete a lock and introduce races.
- Persist a bounded metadata cache shared by Home/Discover/autoplay. Expired
  playable stream URLs are not durable catalogue data. Show usable cached content
  promptly, then refresh; retry partial failures without marking them permanently
  completed or hammering the provider.

### D2. Identify recordings correctly

Separate provider ID, canonical recording identity and display text. Use reliable
provider identifiers where available; otherwise combine conservative title/credit
normalisation and duration tolerance. Keep meaningful version information.

Treat wrong content type, explicit rejection and duplicate recordings as hard
exclusions. Treat uncertain metadata or recent exposure as separate ranking
signals. Avoid rejecting a legitimate song merely because its title contains
"Cover" or "Remix". Default autoplay should still exclude the reported trailers,
lyric reuploads, unwanted edits and bass-boost copies; explicit user selection of
a remix must remain possible. Test same-title songs by genuinely different artists,
collaborations, Topic/VEVO formatting, multilingual titles and accents.

### D3. Rank each surface for its purpose

| Surface | Promise | Proposed behaviour |
|---|---|---|
| Autoplay | Keep this session coherent | Strong seed/session fit, no repeated recording variants |
| Your rotation | Music the user actually returns to | Meaningful repeats, completions and saves |
| Discover | Related music beyond recent listening | Familiar context plus controlled exploration |
| Fresh finds | Music new to this listener | Exclude recent canonical recordings; do not imply a recent release date |

Use a small deterministic, versioned ranker first. Inputs: provider relevance,
seed relationship, recent-session fit, decayed artist affinity, audible listening,
completions/replays, saves, negative feedback and metadata confidence. Derive the
profile off the playback tick. Avoid making one unusual session erase long-term
taste or making all recommendations copies of liked songs.

Apply diversity after ranking: no three consecutive same-artist recommendations
when eligible alternatives exist, and a configurable artist-share limit for
Discover. Respect an explicitly requested artist station or manual queue instead
of applying the same diversity rule everywhere. Never reorder the user's manual
queue as a side effect of refreshing recommendations.

Show explanations only when grounded, such as "Because you listen to Seedhe Maut".
Add local debug diagnostics for source, canonical key, rejection/ranking reasons
and ranker version, with redaction and a clear action; exclude tokens/stream URLs.

### D4. Recommendation acceptance fixtures

Include lyric/video/bass-boost duplicates of one song, unrelated trailers, same
title/different artists, meaningful remix titles, collaboration/Unicode variants,
new users, repeated listening versus many one-offs, mixed tastes, negative feedback,
manual skips versus calls, sparse results, offline/cache/rate limits and stale queries.

Required gates: zero forbidden-content/duplicate leakage in curated fixtures;
every published complete mix has ≥10 unique eligible recordings; requested shelf
counts are met when enough valid fixtures exist; no filler added to reach a number;
one in-flight request per identical key; no recommendation calls from playback
ticks; slow background discovery cannot monopolise playback resolution.

Compare before/after top-10 relevance on a small labelled seed set, repeat rate,
artist diversity and user feedback. Treat real-world skip-rate changes as noisy
observations, not proof of quality from a handful of listens. No large model,
server account or extra cloud infrastructure is required for this first version.

## 8. Phase E — redesign Activity around the user's feedback

Proposed screen, to refine after the user describes what feels wrong:

1. A clear month selector with labelled previous/next buttons and saved selection.
2. An artwork-tinted monthly summary: total listening time and the leading artist,
   with three compact cards for songs, artists and qualified plays where available.
3. A daily listening chart with tap details and accessible text summaries. Legacy
   v0.13 months show totals only, with an honest unavailable-data state for days.
4. Top artists with artwork/fallback initials, rank, minutes and proportional bars;
   top songs with cover, title, artist, minutes and qualified-play count.
5. Tap an artist to see the songs contributing to that total. Songs support play,
   play next and library actions using the normal queue rules.
6. A small, evidence-based insight such as a newly discovered artist or most-played
   day. Show comparisons only for comparable periods; partial-month data must not
   masquerade as a completed-month comparison.
7. Proper empty/loading/error states, useful first-listen guidance and a clearly
   scoped data-clearing control. Do not create empty decorative charts or fake stats.

Use the existing artwork palette and matte frost sparingly, with readable numeric
hierarchy. Animate month changes and bars briefly; do not replay count-up animations
every 15-second data refresh. Defer share cards, gamification and extra metrics until
the core presentation and calculations are accepted.

## 9. Phase F — layouts that adapt to the available screen

Use current window width **and height**, not a hard-coded device model or a scaled
phone screenshot. Width classes are a useful foundation; compact height, split
screen and folds require additional handling. [Android adaptive guidance](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes)

| Window scenario | Layout direction |
|---|---|
| Compact portrait | Single column, bottom navigation, responsive cards and anchored playback controls |
| Short landscape / multi-window | Compact header/artwork; side-by-side content where it fits; seek and transports stay reachable |
| Medium/expanded tablet | Navigation rail, constrained content width, multi-column Home/Activity and optional player/content panes |
| Foldable | Respect hinge/posture and resize without losing selected song, month, queue or scroll state |
| Large font / display zoom | Reflow action rows, grow content, preserve labels and 48 dp phone touch targets |

Audit every user flow: Home, Search, keyboard/history, albums, Library, playlists,
import/download dialogs, all player designs, queue, lyrics/share selection, Activity
and settings. Move secondary actions into an accessible menu when the header is too
narrow; never hide essential controls through clipping or shrinking text to fit.

Anchor the player/lyrics transport area while content scrolls. Compute artwork from
the remaining bounds, account for system bars/cutouts/IME, avoid double insets, and
preserve scroll/navigation state on resize. Car layouts remain host/templates-based;
phone responsive Compose layouts are not projected directly onto the dashboard.

Test representative widths 320/360/412/600/840/1200 dp, heights including 320/480 dp,
portrait/landscape, font scales 1.0/1.3/2.0, gesture/three-button navigation, light/dark
and long/RTL text. This is a defined support matrix, not a guarantee about every
possible screen without testing. Extend the same visual specification to iOS only
in a separately verified SwiftUI pass.

## 10. Phase G — smoother motion without extra weight

Establish shared motion values rather than adding animation independently to each
screen. Initial design targets, subject to real-device tuning:

| Interaction | Starting specification |
|---|---|
| Press/selection/like | 120–180 ms; small scale or tint response |
| Tab/content change | 180–260 ms fade/short slide; retain list position |
| Player expand/collapse and queue/lyrics | 280–360 ms; interruptible, correct Back behaviour |
| Next/previous cover | 400–550 ms directional motion; maintain direction under rapid taps |
| Ambient artwork colour | 900–1,200 ms coordinated fade; avoid stacked competing fades |
| Lyric following | 220–350 ms line reposition, stable text measurement and retained manual-scroll control |
| Activity month/chart | 200–350 ms; update once per interaction, not per playback tick |

Profile before changing state architecture. Split frequently changing position/
progress from library/catalogue/navigation state. Let only the progress and lyric
parts observe fast changes; keep lists and Activity off the 40 ms update path.
Defer animation reads to layout/draw where appropriate, reuse bitmaps/derived word
boundaries, and bound artwork caches. Do not add continuous full-resolution blur
or animated noise. [Compose performance phases](https://developer.android.com/develop/ui/compose/performance/phases)

Keep lyric line heights stable, cancel an old auto-scroll before starting another,
avoid fighting a manual drag, and provide a return-to-current-line action. Retain
the distinction between genuine word timestamps and estimated word following.
Pause vinyl/decorative motion when hidden, paused or backgrounded. Honour reduced
motion/system animation settings; animations must never delay transport commands,
change audio timing or alter haptic scheduling.

Measure with profileable/release-like builds rather than treating debug performance
as representative. Use traces/JankStats on the M30s and a newer device if available.
[JankStats](https://developer.android.com/topic/performance/jankstats)
Provisional targets: warm scrolling/transitions near the 60 Hz frame budget,
<5% janky frames in scripted warm flows and no new app-caused >100 ms stalls.
Record device/build, three repeated runs, CPU/frame percentiles, memory, battery
conditions and cache state. These are targets to test, not measurements obtained today.

## 11. Validation, release and rollback gates

1. Add regression tests with each behavioural change: clocks/month boundaries,
   migration/idempotency, ranking/identity, car search and command authorization.
2. Exercise pause/resume/seek/blending during catalogue work, screen changes,
   foreground/background transitions, network failure and library edits.
3. Run meaningful layout/Compose tests for small heights, large fonts, lyric
   controls, search keyboard, Activity drill-down and navigation restoration.
4. Inspect actual screenshots and run device journeys. No connected car/device
   means the corresponding check stays unverified, even if compilation passes.
5. Check cold/warm performance and APK size. Investigate a >10% size increase from
   the 17.9 MB v0.13 baseline; an optional CAL build must account for its extra size.
6. Stage separate internal checkpoints; keep a usable standard-car build if the
   custom-template path is blocked. Never delete v0.13 until a replacement works.
7. Freeze code before the final full build/test/lint pass; use one worker on this
   machine when memory is constrained. Avoid repeated full runs after cosmetic
   document changes. Stop build daemons after packaging.
8. Produce a signed update APK, matching source archive/hash, installation notes,
   a feature/limitation table, screenshots from the actual build and verification
   report. Version number is assigned at release, not assumed by this plan.
9. Distinguish implemented, compiled, device-tested and car-tested claims. Do not
   publish a new GitHub release or mark all platforms updated from planning work.
